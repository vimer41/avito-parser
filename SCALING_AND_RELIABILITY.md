# Масштабирование и надёжность мониторинга

## Что изменено

- Источник — нормализованный URL с сохранением города, категории, запроса, цены,
  радиуса и `bt`. Трекинг, фрагмент, номер страницы удаляются; сортировка `s=104`.
  Разные фильтры не объединяются в более широкий поиск: полнота такого объединения
  не установлена.
- Планировщик обслуживает старейший дедлайн, держит не более одной проверки на
  источник и чередует повторы с обычными проверками. По умолчанию максимум два
  отложенных повтора с задержками 5/10 секунд, а не передача 403 другому воркеру.
- Следующий успешный опрос отсчитывается от старта проверки, не её окончания.
  Пропущенные тики не воспроизводятся пачкой. При старте источники разнесены на
  15 секунд; новые источники ставятся немедленно после обновления БД (раз в секунду).
- HTTP-сессии сохраняются. Вызовы `curl_cffi.Session.request` получают общий FIFO
  бюджет скорости и параллелизма. Сюда входят калибровка, редиректы, карточки и
  вложенные запросы существующих обработчиков проверок сайта. HTTP выполняется в
  потоке, не в event loop. Асинхронный транспорт пока не менялся.
- 403/429, неизвестные проверки, серверные ошибки, таймауты и отсутствие каталога
  различаются. `Retry-After` соблюдается всеми сессиями; успех старого запроса не
  отменяет активную паузу. После паузы скорость восстанавливается постепенно.
  403 не объявляется доказательством блокировки всего IP.
- Убран скрытый предел 25 карточек и для SSR, и для HTML. Разрешена только явная
  следующая страница того же поиска. По умолчанию не более двух страниц и общий
  дедлайн сбора 45 секунд. Недопроверенное продолжение отмечается `coverage_gap`.
- Калибровка одинаковых поисков разделяет краткоживущий снимок и один выполняющийся
  запрос. Создание радара и запись исходных объявлений атомарны. Пустой снимок
  корректен; миграция существующих радаров аддитивная и не сбрасывает `seen_items`.
- Даты `сек.`, `мин.`, `ч.` разбираются; время «сегодня» интерпретируется в МСК.
  Неизвестный/некорректный возраст не принимается за свежесть, но и не записывается
  как просмотренное объявление: следующая проверка может уточнить метаданные.
- Свежесть проверяется при обнаружении. Принятое уведомление не удаляется лишь
  потому, что долго ждало в SQLite-outbox. Удаление радара, отзыв доступа,
  стоп-слова и ЧС продавцов по-прежнему проверяются перед доставкой.
- Если Telegram `file_id` уже известен, отправляется фото. Иначе немедленно
  отправляется текст, цена и ссылка без скачивания изображения. Фоновая загрузка
  фотографий в этой итерации не добавлена.

## Стартовые настройки

| Настройка | Значение по умолчанию | Смысл |
| --- | ---: | --- |
| `AVITO_REQUESTS_PER_SECOND` | 0.5 | Общий лимит стартов HTTP, без начального burst |
| `AVITO_MAX_IN_FLIGHT` | 2 | Число одновременных HTTP, независимо от 4 воркеров |
| `AVITO_BLOCK_BASE_COOLDOWN` | 30 | Начальная общая пауза в секундах |
| `AVITO_BLOCK_MAX_COOLDOWN` | 900 | Предел экспоненциальной паузы; `Retry-After` может быть больше |
| `AVITO_FETCH_TIMEOUT` | 45 | Бюджет времени сетевой операции/сбора |
| `AVITO_MAX_REQUESTS_PER_FETCH` | 8 | Предел HTTP на получение страницы, включая вложенные запросы |
| `AVITO_MAX_PAGES_PER_SCAN` | 2 | Предел страниц одного точного источника (1..5) |
| `SCAN_MAX_INTERVAL` | 120 | Предел адаптивного **целевого**, не гарантированного интервала |
| `SCAN_BUDGET_UTILIZATION` | 0.8 | Доля бюджета для каталога с резервом на дополнительные запросы |
| `SCAN_MAX_RETRIES` | 2 | Ограниченные повторы (0..3) |
| `INITIAL_SNAPSHOT_TTL` | 25 | Время переиспользования снимка для калибровки |

Это осторожная исходная конфигурация, **не подтверждённая разрешённая или безопасная
частота Авито**. Не увеличивайте её ради цифры 350 без согласованных измерений.
`PROXY_POOL_FILE` не реализован и больше не снимает ограничение воркеров; весь
активный сетевой путь использует только `PROXY_URL`. Бюджет общий в пределах одного
процесса. Несколько процессов с тем же внешним каналом потребуют внешнего общего
лимитера; запускать их для умножения нагрузки нельзя.

При невозможности уложиться в целевые интервалы выводится `overloaded=true`.
Пропускная способность не «исправляется» превышением HTTP-бюджета: фактический
интервал может быть больше 120 секунд. Также требуется учесть настройки свежести
и приток объявлений: ни первая страница, ни две страницы не доказывают полноту
при большом разрыве между проверками.

## Офлайн-модель 350 подписок

`tools/simulate_scheduler.py` моделирует тот же алгоритм без импорта бота, БД или
HTTP. Сценарии: 10, 50, 100 и 350 уникальных источников; можно задать бюджет,
время ответа, число HTTP-слотов и частоту моделируемых ошибок.

Пример аргументов: `--subscriptions 350 --sources 10 50 100 350 --seconds 1800
--rps 0.5 --latency 1.5 --workers 2`. Для ошибок: `--failure-every 5`.

Модель предполагает один запрос на проверку. Редиректы, страницы, восстановление
сессии и реальные 403 ухудшат результат. При 350 уникальных поисках даже целевые
15/25/60 секунд требуют соответственно 23.3/14/5.8 успешных запросов в секунду:
это арифметика спроса, а не допустимые скорости. Надёжность доставки не отменяет
невозможность обнаружить то, что источник не успел показать в пределах окна.

Результат офлайн-прогона (1800 секунд, 350 подписок, 0.5 запроса/с, ответ 1.5 с):

| Уникальных источников | Стартов HTTP | p95 повторной проверки | Перегрузка целевого бюджета |
| ---: | ---: | ---: | --- |
| 10 | 720 | 25 с | Нет |
| 50 | 750 | 120 с | Да — требуется часть 20% резерва |
| 100 | 900 | 200 с | Да |
| 350 | 900 | 700 с | Да |

При искусственной ошибке каждого пятого запроса все 350 источников всё равно
получили проверку, p95 повторного опроса — 724 с. Это проверка отсутствия голодания,
а не модель реальных блокировок: паузы `Retry-After` могут увеличить задержки.

## Проверки и наблюдение

Офлайн-тесты запускаются через `tools/run_offline_tests.py`: HTTP-клиенты и
внешние сокеты запрещены, SQLite/cookies/logs изолированы. Можно передать имена
модулей для прицельного прогона, например `tests.test_scaling tests.test_reliability`.

Ежеминутный лог `Мониторинг` содержит число подписок и источников, ожидающие
дедлайны, старейшую задержку, повторные задачи, фактический разрыв между стартами,
успехи/ошибки, gaps, оценку стоимости проверки в HTTP и состояние общего бюджета.
Поле `outbox` показывает число ожидающих и занятых задач, возраст самой старой.
`Delivery result` содержит задержку от обнаружения до подтверждения доставки.

Следующий этап — низконагрузочные разрешённые измерения: реальные число источников,
HTTP/проверку, p50/p95 повторного опроса и discovery-to-send, статусы ответов,
возраст outbox и пробелы покрытия. Боевой бот и сетевые нагрузочные проверки в
рамках этой итерации не запускаются. Официальный API произвольного поиска по
всему рынку не подтверждён.

SQLite-outbox сохраняет семантику **at least once**: при падении между успешным
ответом Telegram и подтверждением в БД возможен повтор. Exactly-once доставка
не обещается. Объявления с постоянно неизвестным возрастом не доставляются без
достоверных метаданных, но и не теряются в `seen_items`.
Старые неподтверждённые outbox-записи с неизвестным возрастом освобождаются без
отметки «просмотрено», чтобы уточнённое объявление могло снова пройти сбор.
